# 要件定義書 (Requirements Specification)

## 1. 背景と目的

### 1.1 背景
ソフトウェア開発において、不具合（バグ）やQA課題のライフサイクル管理は品質保証の要です。前職での実務では **Azure DevOps（Boards / Test Plans）** を活用し、テストケースのインポート、テスト実行結果の記録、不具合チケットのステータス管理を実施してきました。
また、APIリグレッションテストには **Bruno** を採用し、アサーションを用いた合否判定を行っていました。

### 1.2 目的
本システム（QA Tracker）は、実務で培った「QAプロセスのベストプラクティス」を反映したチケット管理システムです。
単に動くアプリを作るのではなく、**SDET（Software Development Engineer in Test）** として、以下の2つを実現することを主眼としています：
1. **実務レベルのデータ構造・状態遷移を持つシステムの開発**
2. **自動テストツール（Bruno）からテストしやすい「テスト容易性の高いRESTful API」の提供**

---

## 2. システムの利用者とユースケース

### 2.1 主な利用者
- **QAエンジニア / テストリード**: 不具合の起票、再現手順の記録、ステータスの追跡
- **開発エンジニア**: 不具合内容の確認、原因調査、改修後のステータス更新
- **テスト自動化エンジニア (SDET)**: APIを介したチケットデータ作成・更新および自動テスト検証

### 2.2 主要ユースケース
```mermaid
flowchart LR
    QA["QAエンジニア / テストリード"]
    DEV["開発エンジニア"]
    SDET["自動テスト (Bruno / CI)"]

    QA -->|1. バグ起票 (New)| System[("QA Tracker")]
    DEV -->|2. 調査着手 (Active)| System
    DEV -->|3. 改修完了 (Resolved)| System
    QA -->|4. 確認・クローズ (Closed)| System
    SDET -->|5. API自動回帰テスト| System
```

## 3. 機能要件 (Functional Requirements)

| 機能ID | 機能名 | 概要 | 詳細仕様 |
| :--- | :--- | :--- | :--- |
| **F-01** | チケット起票 | 不具合・QAチケットを新規登録する | タイトル、再現手順、期待結果、実際の結果、優先度、重大度を入力して登録。初期ステータスは `New`。 |
| **F-02** | チケット一覧取得 | 登録されているチケット一覧を取得する | 全件取得に加え、ステータス別（`status`）での絞り込みを可能とする。 |
| **F-03** | チケット詳細取得 | 指定IDのチケット詳細情報を取得する | チケットが存在しない場合は適切なエラー（404 Not Found）を返却する。 |
| **F-04** | ステータス更新 | チケットのステータスを進行させる | 許可された遷移ルール（後述）に則り、ステータスを更新する。不正な遷移は拒否する。 |
| **F-05** | 入力バリデーション | 不正なリクエストを防止する | 必須項目の未入力、許容外の文字数、不正な優先度/重大度値をチェックし、400 Bad Requestを返却。 |
| **F-06** | チケット削除 | 不要になったチケットを削除する | 指定IDのチケットを削除する。 |

## 4. 業務ルール・制約（Azure DevOps運用の知見の反映）

### 4.1 管理項目
Azure DevOpsの実務運用に基づき、バグ調査に必要な情報漏れを防ぐ設計とします：
- **タイトル (`title`)**: 必須（1〜100文字）
- **再現手順 (`reproductionSteps`)**: 必須（ステップ箇条書き）
- **期待される結果 (`expectedResult`)**: 必須
- **実際の結果 (`actualResult`)**: 必須
- **優先度 (`priority`)**: `Low`, `Medium`, `High`, `Critical`
- **重大度 (`severity`)**: `Minor`, `Major`, `Critical`, `Blocker`
- **ステータス (`status`)**: 後述のステータス管理に準拠

### 4.2 ステータス遷移ルール
不具合管理における「勝手なクローズ」や「不正な戻り」を防ぐため、厳格なステータス遷移を定義します：
- **`New`**（新規起票） ➔ **`Active`**（調査・修正中）
- **`Active`** ➔ **`Resolved`**（修正完了・QA確認待ち）
- **`Resolved`** ➔ **`Closed`**（QA確認完了・クローズ） または **`Active`**（再現したため差し戻し）
- ※ `Closed` からの再オープンは `Active` へのみ許可

## 5. 非機能要件 (Non-Functional Requirements)

### 5.1 テスト容易性 (Testability) ★最重要
- **予測可能なAPIレスポンス**: 成功時・失敗時ともに統一されたJSONフォーマットで返却し、Brunoでのアサーションを容易にする。
- **適切なHTTPステータスコード**: `200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found` などを厳格に使い分ける。
- **明確なエラーメッセージ**: なぜ失敗したか（どのフィールドが不足しているか）をJSONレスポンスに含める。

### 5.2 自動テスト連携 (Automation Readiness)
- Bruno CLI (`bru`) を用いて、コマンドラインから一括実行可能であること。
- テスト実行前後でデータがクリーンアップできる仕組み、またはリクエスト間で変数（チケットID等）を引き渡せる設計とすること。
